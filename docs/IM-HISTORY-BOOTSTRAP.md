# 1.3.19-im.7：修正历史读取初始化与参数位置

内部版本号 67，基于 im.6。用户反馈 380006 仍无具体说明。本次不是再次扩充错误文案，而是修正与原始调用样例不一致的请求过程。

## 已查明的接入差异

重新完整检查 [ccloli/Tieba-Chat 原始代码](https://github.com/ccloli/Tieba-Chat/blob/8efb4cd31f6217e53d479a362d68804e5b0ddc6f/tb_chat.user.js)：

1. `get_latest_msg` 首次调用 `/c/s/recentmsg`，初始 `msg_id=0`。根据返回消息确定最早的消息编号。
2. 点击加载更早消息时，`get_early_msg` 才调用 `/c/s/historymsg`，传入最早的消息编号。
3. 两者都是 POST，但业务参数与签名放在 URL 查询中，发送空请求体。网页已有 Cookie 登录态；样例查询中的 BDUSS 被注释。

im.5/6 漏掉了 recentmsg 初始化，直接请求 historymsg、msg_id=0；也把参数放进了表单，并将 BDUSS 加入表单签名。这些是源码核对能够确认的差异。没有登录账号的探测总在登录检查阶段失败，不能证明后续业务参数被正确处理。

## 本版行为

- 点击同步时，第一批改用 recentmsg、msg_id=0；有更多历史时，后续点击用 historymsg、msg_id=上一批最早编号。
- 业务参数按原样例放到查询中，按参数名排序拼接原始值并计算小写 MD5 签名。BDUSS 只在 Cookie 请求头中，不出现在 URL 或空请求体。
- 错误提示注明是“最近消息初始化失败”还是“更早历史读取失败”，并保留 im.6 的安全错误说明处理。
- 历史持久化、重复导入去重、非文本消息提示、未读保护、账号隔离沿用已有实现。重新进入聊天后会从 recentmsg 开始。

## 验证边界

请求级测试验证初始化端点、后续历史端点、查询参数位置、空 POST 请求体、Cookie 登录态、URL 不含凭据，以及固定签名向量。已有历史解析和错误说明回归继续运行。

尚未用真实登录账号验证。修正的是已经确认的调用差异，不代表已证明 380006 一定由这两处引起，也不保证旧接口仍保存或开放全部聊天历史。安装后需要查看首次 recentmsg 是否成功，以及后续 historymsg 是否成功；不应把失败等同于“账号没有历史”。
